Fundamentos · §2

El servicio es dueño de su base de datos

Los usuarios llegan por el API Gateway, con HTTPS y un token. Otros microservicios llaman a las rutas /internal por la red interna. Nadie más lee la base de datos: ni el cliente ni otro servicio.

Las probes /health quedan fuera del prefijo /api y de la versión.

Fundamentos · §3

Cinco capas, una sola dirección

Los módulos usan common; common no conoce a ningún módulo.

  • bootstrapmain.ts y app.module.ts: arrancan, aplican lo transversal y registran los módulos.
  • modulesUna carpeta por capacidad de dominio: resource, users, sessions…
  • healthProbes de salud del proceso y sus dependencias.
  • commonSobre de respuesta, excepciones, paginación y guards. Sin dominio.
  • configLee y valida el entorno; arma la conexión a la BD y el logger.

Un módulo no lee process.env: recibe la configuración por ConfigService.

En la consola, la columna bootstrap es todo lo que Nest aplica antes y después del controller: el ValidationPipe, el interceptor que arma el sobre y el filtro que traduce los errores.

El módulo crece · §4.9

Un módulo nace como contrato

Primera etapa: existen las rutas, los DTOs y la documentación. La lógica todavía no: el service devuelve datos de ejemplo tipados.

// modules/sessions/sessions.service.ts
@Injectable()
export class SessionsService {
  revokeSession(_sessionId: string): Promise<AckResponse> {
    return Promise.resolve({ ok: true });
  }
}

Así están hoy los nueve módulos de Identity. Las carpetas business/, entities/, mappers/ y repositories/ existen vacías, con .gitkeep, para fijar la forma.

En la consola, la petición llega al service y vuelve sin tocar la base de datos.

El módulo crece · §4.9

Aparecen datos propios

Con una tabla propia llegan tres piezas: la entidad (la forma en la BD), el repository (la única puerta al ORM) y el mapper (entidad → DTO). El service deja de devolver stubs.

async findOne(id: string): Promise<ResourceResponseDto> {
  const resource = await this.repository.findOneById(id);
  return this.mapper.toResponseDto(resource);
}

La petición ahora baja hasta la BD y la respuesta trae el registro real de RES-002.

El módulo crece · §4.9

Aparecen las decisiones

Cuando hay un if de negocio, un cálculo o una máquina de estados, aparece business/. El service ya no decide: encadena reglas.

async calculate(id: string): Promise<ResourceCalculationDto> {
  const resource = await this.repository.findWithRelationsForCalculation(id);
  return this.business
    .init(resource)
    .validateEligibility()
    .applyDraftPenalty()
    .applyVolumeDiscount()
    .enforceMinimumAmount()
    .round()
    .getCalculationResult();
}

El inspector sigue la cadena sobre RES-001: está en DRAFT, así que paga la penalización del 5 %.

El módulo crece · §4.9

¿Qué forma necesita tu módulo?

Un módulo suma piezas cuando aparece lo que las justifica, no antes. Responde y te dice por dónde empezar.

Roles · §5

El controller recibe y delega

Declara la ruta, valida la entrada con DTOs y pipes, documenta el endpoint y devuelve el dato plano del service. No decide, no consulta, no arma el sobre ni captura excepciones.

@Get(':id')
@ApiStandardResponse(ResourceResponseDto)
findOne(@Param('id', ParseUUIDPipe) id: string) {
  return this.service.findOne(id);
}

Prueba un id que no es UUID: el pipe lo rechaza antes de que el controller se entere.

Roles · §5

El service orquesta

Coordina repository, business, mapper y services de otros módulos. No tiene if de existencia, ni cálculos, ni consultas. Es la única pieza que el módulo exporta.

async update(id: string, dto: UpdateResourceDto) {
  const resource = await this.repository.findOneById(id);
  const updated = this.business
    .init(resource)
    .validateEligibility()
    .applyChanges(dto)
    .getEntity();
  const saved = await this.repository.save(updated);
  return this.mapper.toResponseDto(saved);
}

Cada línea es un paso con dueño. Si algo falla, la excepción sube sola: el service no la atrapa.

Roles · §5

El business decide, sin await

Toda decisión de negocio vive aquí, con interfaz fluida: init() abre la cadena y resetea el estado, cada regla devuelve this y un método terminal entrega el resultado.

const RULES = {
  DRAFT_PENALTY_RATE: 0.05,
  VOLUME_DISCOUNT_THRESHOLD: 1_000_000,
  VOLUME_DISCOUNT_RATE: 0.02,
} as const;

@Injectable({ scope: Scope.TRANSIENT })
export class ResourceBusiness { … }

Es TRANSIENT y síncrono. El service singleton comparte su instancia entre peticiones, y es seguro porque la cadena no tiene await e init() lo resetea todo. Si una regla necesita datos, el service los trae antes de init().

Roles · §5

El repository falla pronto

Es la única pieza que toca el ORM. Si busca por id y no encuentra, lanza EntityNotFoundException. Devuelve Promise<Resource>, nunca Promise<Resource | null>, y por eso el service no tiene ningún if.

async findOneById(id: string): Promise<Resource> {
  const resource = await this.repository.findOne({ where: { id } });
  if (!resource) {
    throw new EntityNotFoundException('Resource', id);
  }
  return resource;
}

Los listados devuelven PaginatedResultDto<T>, nunca un array suelto.

Roles · §5

La entidad no sale del módulo

El mapper convierte la entidad en DTO con funciones puras. Es el único lugar donde se arma un DTO de salida.

Una petición · §7.1

Leer: los datos bajan ya traducidos

Repository → Service → Controller. Cada salto entrega algo más cercano al contrato: una fila, una entidad, un DTO, un sobre.

  • pipeParseUUIDPipe valida el id antes de entrar.
  • repositoryHace el SELECT y entrega la entidad.
  • mapperLa convierte en ResourceResponseDto.
  • controllerDevuelve el DTO tal cual: dato plano.
  • interceptorLo envuelve en { success, data, meta, … }.

Edita la URL de la consola con otro id de la tabla y vuelve a enviar.

Una petición · §7.3

Cada capa lanza lo suyo; el filtro traduce

Nadie fuera de common/filters decide un status HTTP. Las capas lanzan excepciones de dominio y suben sin envolverse hasta el filtro global.

Caso borde

code tiene índice único, pero ensureCodeIsAvailable() no ve los registros borrados con soft delete. Si reutilizas el code de un recurso eliminado, el INSERT choca y sale un 500 en vez de un 409.

Una petición · §7.4

Listar: siempre paginado

El DTO de consulta extiende PaginationQueryDto. El repository devuelve PaginatedResultDto, y el interceptor pone los items en data y la paginación en meta.

export class FindResourcesQueryDto extends PaginationQueryDto {
  search?: string;
  status?: ResourceStatus;
  minAmount?: number;
  sortBy: 'createdAt' | 'name' | 'amount' | 'code' = 'createdAt';
  sortOrder: 'ASC' | 'DESC' = 'DESC';
}

Una petición · §15

Un solo sobre para todo

Éxitos y errores salen con la misma forma. Ningún controller la arma: el interceptor envuelve los éxitos y el filtro global, los errores.

{
  "success": true,
  "statusCode": 201,
  "message": "Recurso creado correctamente",
  "data": { … },
  "meta": { "timestamp": …, "path": … },
  "errors": null
}

El mensaje sale de @ResponseMessage(); si el handler no lo declara, es "OK". Un 204 no lleva cuerpo.

El DELETE es soft delete: la fila queda en la tabla con deletedAt y las lecturas siguientes responden 404.

Plataforma · §8

Si el entorno no es válido, no arranca

Toda variable se declara y valida en un solo contrato, config/env.validation.ts. Si falta o es inválida, el proceso no levanta y el error dice cuál.

NODE_ENV
DB_SYNCHRONIZE
DB_DATABASE
Base de datos

Prueba DB_SYNCHRONIZE=true con qa: lo peligroso depende del entorno, y la variable solo puede apagarlo, nunca encenderlo fuera de su entorno.

Dependencias · §6

Hacia afuera: el service y los DTOs

El @Module registra todas las piezas como providers y exporta solo el service. Entidad, repository, business y mapper son privados.

@Module({
  imports: [TypeOrmModule.forFeature([Resource])],
  controllers: [ResourceController],
  providers: [ResourceService, ResourceBusiness,
              ResourceRepository, ResourceMapper],
  exports: [ResourceService],
})

Un controller solo inyecta el service de su módulo. Fuera del repository, nadie inyecta Repository<T>, DataSource ni EntityManager.

Dependencias · §6.1

Entre módulos, sin ciclos

Si A necesita datos de B, importa BModule e inyecta BService. Si solo necesita la forma, importa el tipo desde B/dto. Hoy los módulos de Identity solo comparten tipos.

Líneas punteadas: solo tipos de dto/, sin dependencia en tiempo de ejecución.

Si dos módulos se necesitan mutuamente, la pieza común baja a un tercer módulo o a common si no tiene dominio. forwardRef no se usa para esconder un ciclo.

Dónde va · §9

¿Dónde va cada cosa?

Primero se pregunta si tiene dominio. Si no tiene, va a config o common; si tiene, va al módulo dueño, en la pieza que corresponde a lo que hace.

Fin del recorrido

Toda la arquitectura, en una petición

Por módulo de dominio y, dentro, por rol. Dependencias en una sola dirección. Cada pieza hace una sola cosa. La entidad no sale del módulo. Un solo sobre de respuesta. Cada capa falla en su lugar y una sola pieza traduce. Seguro por defecto.
